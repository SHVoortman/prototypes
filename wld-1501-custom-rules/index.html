NEW

What this prototype is testing. Whether an administrator can express a real shop rule using a basis, stacked conditions, an adjustment, a stage and a name, and whether the difference between "for each that matches" and "if any matches" is obvious enough at the point of choosing.

Two things deliberately absent. There is no generated sentence describing a saved rule, because word order and grammar do not survive translation; rules are summarised as discrete labelled values instead. And there is no warning about rules that overlap or never fire, because the rule name is what carries the intent.

The container is not a field. When a condition uses "if any matches" or "if none match", what it counts across follows from the basis rather than being chosen separately, so it is shown as read-only text.

Percentages are a Could, not agreed. The Time and Percentage toggle in step 3 is REQ-12 and is here to be argued about. A percentage is measured against the standard time before any rule runs, never against the running total, and percentages against the same thing add rather than compound. That is what keeps rule order irrelevant. If percentages ever applied to the running total, an administrator would have to control the order rules are worked out in and this screen would need reordering as well.

Why the heavy plate rule names two shapes. A welded plate arrives as Plate if it was cut from plate steel and as Flat bar if it was cut to length from bar stock, so a rule meant to catch end plates has to allow both. The weight condition is what keeps the stiffeners out. This is the reason the shape picker is a checkbox list rather than a dropdown.
